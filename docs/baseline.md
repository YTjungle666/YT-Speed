# 基线数字（P0 标定结果）

本文件是 `PLAN.md` §0.3 / §0.3b / §0.5 的落地副本，供后续实现阶段对照。
所有数字都来自实测；环境变了（换机、换网卡、换对端、开/关 offloading）必须重测。

## 环境

| 项 | 值 |
|---|---|
| 服务端 | 服务端容器（Debian LXC），192.0.2.10，非特权 LXC，8 vCPU |
| 网卡 | `eth0@if31` veth，MTU 1500（`/sys/.../speed=10000` 是占位值，不是 10G 的证据） |
| 客户端 | 192.0.2.30 物理 Windows 机，Edge/Chrome |
| 路径 | 同网段 L2，不经路由（经 路由器 转发会把带宽折半） |

## 链路能力（iperf3）

| 场景 | 数值 |
|---|---|
| 宿主内 CT→CT 单流 | 80–100 Gbit/s（内存带宽，非链路） |
| 宿主内 CT→CT 6 流 | 113–182 Gbit/s |
| **服务端容器 → 192.0.2.30 8 流** | **9.34–9.39 Gbit/s** |
| 服务端容器 → 192.0.2.30 单流 | 3.56–3.77 Gbit/s |
| 重传 | 整轮唯一一条 12/1138，≈0 |

## 浏览器（同一台 Windows，同一页面）

| 方向 | 方案 | 数值 |
|---|---|---|
| 下载 | fetch + `getReader()`，**Web Worker**，8 路，1 MiB 帧 | **8.2–8.5 Gbit/s**（典型 8.24 / 8.31 / 8.49） |
| 下载 | 同上但跑在主线程 | 6.6–7.9（Worker 约 +9%） |
| 下载 | 单流 HTTP | 1.5–1.7（比 iperf3 单流还低一半） |
| 上传 | **WebSocket 单连接** | **9.44 Gbit/s（线速）** |
| 上传 | XHR 分块（8/20/32 MiB × 1–6 路） | 1.9–5.2 |

## 下载上限的定位（TCP_INFO，250 ms 采样）

| 指标 | 值 | 含义 |
|---|---|---|
| `sndbuf_limited` | 0 ms | 发送缓冲从不缺 → 服务端不是瓶颈 |
| `busy_time` | ≈100% 窗口 | 内核始终有数据可发 |
| `rwnd_limited` | 113 ms / 250 ms（45%） | 卡在 Windows 通告的接收窗口 |
| 重传 / RTT / cwnd | 0 / 1.36 ms / 241 段 | 链路健康 |

结论：浏览器下载的上限由**接收端窗口**决定（Chrome 每 socket 约 1.4 Gbit/s 的读取速度 →
Windows 把窗口停在约 238 KB），服务端怎么调都到不了 9.4。

## 已实测否掉的方向（不要再试）

| 方向 | 结果 |
|---|---|
| HTTP/2 + TLS（真证书，18 流一条连接） | 3.04 Gbit/s；回环也只有 12–13 且不随流数增长 |
| WebSocket 下载（推模式 / 拉模式，1–16 路） | 2.4–6.1 Gbit/s，连接越多越低 |
| fetch + WS 混合 | 6.16 / 7.06，低于纯 fetch |
| BYOB 读（复用缓冲） | 8 MiB 用了 46 万次 read，平均 18 B/次 |
| 多 origin 分流（2/3 个端口） | 与单 origin 无差别 |
| 16 MiB 大帧 | 与 1 MiB 在噪声内，但多吃 128 MB 缓冲 |
| 服务端发送缓冲/`SO_SNDBUF` 调整 | `sndbuf_limited` 已为 0，无可调空间 |

## P2 服务端验收（`speedtestd`，2026-10-24）

服务端容器 本机回环，8 vCPU，`--listen 0.0.0.0:8080`。限速项在括号内单独标出。

| 项目 | 结果 |
|---|---|
| 下载单流（1 GiB，`ckSize=1024`） | **7,105,179,452 B/s = 56.8 Gbit/s**（阈值 ≥40） |
| 下载 6 路并发（6 GiB） | **6 GiB / 0.280 s = 184 Gbit/s**（阈值 ≥80） |
| WS 上传 10 GiB | 客户端 75.37 Gbit/s；服务端计数 10,737,418,240 B（**与客户端逐字节一致**） |
| WS 上传 20 GiB | 服务端 21,474,836,480 B（一致）；RSS 13.7 → 14.8 MiB（**+1.07 MiB**） |
| HTTP chunked POST 10 GiB | 服务端计数 10,737,418,240 B（一致）；RSS **+4.45 MiB**（阈值 <8） |
| 上传三种形态（CL / chunked / `Expect: 100-continue`） | 各 8 MiB，三种都精确收到 8,388,608 B，均回 `100 Continue` + 200 |
| 随机数据熵 | **7.9998 bit/byte**（1 MiB 样本，256 个值） |
| 连接复用 | `/backend/empty` 连续两次请求 `num_connects` = 1, 0 |
| 下载限速 500 Mbit/s（64 MiB） | 62,435,387 B/s = **499.5 Mbit/s**（99.9%） |
| 上传限速 5000 Mbit/s（WS 2 GiB） | **4.999 Gbit/s**（99.98%），服务端计数 2,147,483,648 B |
| 结算 token | 一次性；二次取回 404，未知 token 404 |

限速实现要点：按“累计字节对应的时刻表”睡眠（deadline pacing），不是每块固定睡——
固定睡眠会把每次调度误差累加，实测差出 7%。上传限速靠延迟读取让接收窗口收缩，
不丢数据，所以客户端看到的数字仍然真实。

`scripts/verify-server.sh` 覆盖上表除吞吐以外的全部项目，可直接跑。

## P3 浏览器引擎（wasm + Worker，本机回环，2026-10-24）

引擎 `speedtest-wasm` 编成 261 KB 的 wasm（未压缩），跑在 Web Worker 里，页面只收 10 Hz 快照。
本机回环数字只说明**代码路径干净**，不代表链路上限（那要等 L2 物理机复验）：

| 项目 | 结果 |
|---|---|
| 只测下载（8 路、1 MiB 帧） | 26.8–27.8 Gbit/s（回环，6.9 s 结束：`time_auto` 按速度自动缩短） |
| 只测上传（WS 单连接） | 14.0–14.4 Gbit/s（回环） |
| 完整 ping→下载→上传 | ping 1.00 ms / jitter 1.14 ms（<1 ms 被上游规则钳到 1）、下载 26.8、上传 14.4 |
| 采样点数 | 146 点（15 s 带 ping 的完整测试；定容上限 2048，永不增长） |
| 上传结算一致性 | 页面值 = 服务端 `bytes/ms × 8 × 1.06`，逐位一致（14,038.87 对 14,039） |

### 这一轮踩到的三个坑（都已修，用例/注释留在代码里）

1. **时钟必须同源**：`start()` 内部用 `Date::now()`（纪元毫秒）、`tick()` 用 `performance.now()`，
   差 1.7e12，core 算出的 `t` 永远是负数，页面卡在 grace 里、永远没有读数。现在 `start()`
   显式接收 `now_ms`，由 JS 传同一个时钟。
2. **1 GiB 请求跑完必须重发**：万兆下 1 秒就结束，8 路会同时停，速率断崖。下载任务改成
   “读完一条立刻再来”（与上游 XHR `onload` 重发一致）。
3. **阶段结束不能立刻停表**：上传结算是“关连接 → 取 token”之后才回来的，一 Done 就停心跳
   会让它永远落不了地——实测客户端“已 send”计数比服务端高 6.6%（14,171 vs 13,292 Mbit/s）。
   现在结束后继续空转 600 ms 收结算，并且 core 允许**迟到结算覆盖已定稿结果**。
4. 附带：静态资产的 `immutable` 缓存不能按扩展名给。`speedtest_wasm_bg.wasm` 是固定名，
   被浏览器按 immutable 缓存后重建也不生效，白等了两轮 15 秒；现在只有**文件名带内容哈希**
   的资产才 immutable。

## P3 L2 复验（192.0.2.30 Windows，Marvell 10G，2026-10-24）

Edge/Chrome 打开 `http://192.0.2.10:8080/`，完整 ping→下载→上传，连跑 3 轮：

| 轮次 | 下载实测 | 上传实测 | ping / jitter |
|---|---|---|---|
| 1 | 7,904.08 Mbit/s | 9,449.57 Mbit/s | 2.00 / 0.95 ms |
| 2 | 7,956.02 | 9,432.18 | 3.00 / 0.00 |
| 3 | 7,436.54 | 9,473.07 | 3.00 / 0.30 |
| **中位** | **7,904.08（7.90 Gbit/s）** | **9,449.57（9.45 Gbit/s）** | — |

- 下载阈值 8 路中位 ≥7.4 Gbit/s → **达标**（7.90）
- 上传阈值 WS 单路 ≥9.0 Gbit/s → **达标**（9.45）
- 三轮 `failed=false`，采样各 146 点（定容）
- 上传三方对齐：页面 9,449.57 / 9,432.18 / 9,473.07 与服务端结算 9.449571 / 9.432182 / 9.473068
  **逐位一致**（差异 <0.01%）——服务端结算是唯一口径

### 与 iperf3 基线对照

| 方向 | iperf3 8 路 | 浏览器实测 | 达成率 |
|---|---|---|---|
| 下载（服务端→客户端） | 9.34–9.39 Gbit/s | 7.90 | 84% |
| 上传（客户端→服务端） | 9.53 Gbit/s | 9.45 | 99% |

下载那 16% 的缺口与 P0 的结论一致：瓶颈在接收端的窗口与读取环路（TCP_INFO：`rwnd_limited≈45%`、
`sndbuf_limited=0`、重传 0），不在服务端。另一个已知开销是 wasm 边界——P0 的纯 JS Worker
路径是 8.24–8.31 Gbit/s，现在是 7.44–7.96，每块数据要过 `JsFuture` + 两次 `Reflect`。
仍在阈值之上，但如果 P4 之后要追这 3–8%，优先把“每块一次跨边界”改成批量读取。

## P3 收尾：XHR 降级、限速语义、legacy 对照（2026-10-24）

### 1. 限速必须是「聚合」的

第一版按“每个响应自己睡”实现，8 路并发时 1000 Mbit/s 的限速会乘成连接数：

| 场景 | 结果 |
|---|---|
| 单路 64 MiB @1000 Mbit/s | 0.640 s，104.8 MB/s（约 838 Mbit/s 含请求头开销） |
| 8 路并发各 64 MiB（旧实现） | 4.8 Gbit/s —— 等于没限 |
| 8 路并发各 64 MiB（`pace::RateLimiter`，单条时间轴） | **512 MiB / 4.303 s = 998 Mbit/s** |

时间轴实现要点：`next` 指针只往前推，**不要**用 `max(next, now)` 把欠账抹掉，
否则定时器过冲会累积；只有空闲超过 1 s 才钳到 now。

### 2. WS 上传限速：先预留再读

“先读一帧、再睡一帧的时间”是两段串行等待（等数据 + 睡眠），1 Gbps 实测只有
0.86 Gbit/s（-14%）。改成**先按上一帧长度预留时间、再 recv**，睡眠期间数据已经堆在
内核缓冲里，醒来即读：

| 方式 | 2 GiB @ 1 Gbit/s |
|---|---|
| 先读再睡 | 19.888 s = 0.864 Gbit/s |
| 先预留再读 | **17.190 s = 0.999 Gbit/s** |

### 3. 限速 1000 Mbit/s 下的页面读数（本机回环，新引擎）

下载实测 999.998 / 上游口径 1060.00；上传实测 998.879 / 上游口径 1058.81；ping 1.00 ms。
两个方向都正好压在限速上，说明服务端节流与页面计时的口径自洽。

### 4. XHR 降级

WS 握手失败或 1.5 s 未 open → 退到 4 路 `POST /backend/empty`（1 MiB 复用缓冲、有界），
页面显式标注「XHR 降级（客户端计数）」。回环实测 2,192 Mbit/s（实测）/ 2,323（×1.06）。
这就是 P0 已经量过的 HTTP 上传天花板，所以它只做降级，不做主路径。

### 5. legacy 对照（正式验收，192.0.2.30，20 轮）

`web/compare.html` 在同一页面交替驱动上游 v6.3.1（XHR 多流）与本引擎（fetch + WS），
服务端 `--max-download-mbps 1000 --max-upload-mbps 1000`，每轮 6 s 下载 + 6 s 上传，
两边都取各自的 ×1.06 口径：

| | legacy（上游） | 新引擎 | 偏差 |
|---|---|---|---|
| 下载中位 | 1,060.42 Mbit/s | 1,060.02 Mbit/s | **-0.04%** |
| 上传中位 | 1,071.43 Mbit/s | 1,057.12 Mbit/s | **-1.34%** |

验收线是“限速 1 Gbps、交替 20 轮、中位偏差 ≤5%”，两个方向都远在门内。
两点说明：

- legacy 的上传中位 1,071 略高于限速 1,060（=1000×1.06），因为它是**客户端按已 send 计数**；
  服务端结算口径（本引擎用的）不会超。这个差异正好印证了 P3 早期“客户端估算偏高”的结论。
- 本机回环预跑时 legacy 波动 766–1061 且出现过一次超时，同一环境下新引擎三轮只差 ±1 Mbit/s；
  在 192.0.2.30 上 20 轮没有出现失败轮次。

## 复现方式

```sh
# 链路
iperf3 -c 192.0.2.30 -t 8 -P 8
# 浏览器：headless 回环对照（证明代码路径干净，1.9 那种低值是 HTTP 请求周期造成的）
google-chrome --headless=new --disable-gpu --no-sandbox \
  --user-data-dir=/tmp/c1 'http://127.0.0.1:PORT/page?auto=dl'
```

单次测量噪声 ±1.5 Gbit/s，任何结论都要 3 次取中位数，并在同一时段跑一次 iperf3 作对照。
